# TB710FU XNU / ramoops 双实时二维码

本组件替换逐检查点两秒回放。两个二维码读取本次启动的实际日志；
屏幕顶部保留固定官方 UniXNU 的绿、蓝、品红三条，每条占
`((rowBytes * height) >> 4) & ~7` 字节。

## 显示与接收

TB710FU 的 3200×2000 帧缓冲并排显示两个实时二维码：

- 左侧 XNU：直接读取独立的 64 KiB XNU 输出环形缓冲。每份文件都带有
  `machine_startup` 前冻结的最多 512 字节早期备份，以及当前最近最多
  3072 字节调试输出。后台线程实际运行前，当前尾部最多 512 字节。
- 右侧 ramoops：直接读取本次启动 ramoops 区域的最近最多 4096 字节；
  后台线程实际运行前最多 512 字节。它是原始日志文本，排除 Linux
  pstore 头、ECC 和旧启动日志，包含尚未换行的尾部。

ramoops 是日志的内存副本，因此两侧文本可能重叠。它们来自独立缓冲，
不能把两个相似的文件当成两份独立的硬件启动证明。

左侧文件的导出元数据明确区分 early backup 与 current tail 的状态、
真实字节范围和长度；随后依次放置两段原始字节。元数据不是 XNU
控制台输出。早期备份只冻结一次，之后每份左侧文件都重复携带它，
不会随环形缓冲覆盖。冻结时若为空或忙，会明确标注，后续日志不被
冒充成早期备份。左侧在这次冻结完成前显示 pending。

文件名使用 `TB710FU-xnu-live-GENERATION-START-END.log` 与
`TB710FU-ramoops-live-GENERATION-START-END.log`。范围 `[START, END)`
标明各自当前尾部在本次启动成功写入字节流中的位置；左侧的完整文件
还包含元数据和早期备份，因此文件大小可以大于 `END - START`。
两侧均为有界快照，不代表整份启动日志。争用丢弃字符单独计数。

每份文件先固定内容，再轮播数据块；每个通道至少发完两轮才更新。
接收使用固定版本 OneSend 原协议。先接收一侧，重置接收器后再接收
另一侧；同一个接收器实例不能混用两个 session。实时文件代次改变
也应重置，或由接收端分别管理 session。小屏无法并排时交替显示。

## 保留与覆盖

短日志通常不容易写满 64 KiB 环形缓冲，但密集循环输出仍可能覆盖
最旧的内容。二维码传输期间文件不会被修改，固定的早期备份也不会
被覆盖；这两项保护不能保证保留每个时刻的完整日志。

若 CPU 卡在关闭中断的循环中，实时轮播也会停下。多帧文件只有已经
接收齐才可恢复；仅拍到停止时的一张码不能保证恢复整个文件。此前的
独立固定单帧显示方案已按用户最新选择改为双实时加文件内早期备份。

## 原生边界

显式参数为 `tb710fu-live-log=1 debug=0x8 -enable_kprintf_spam startup_debug=1`。
`debug=0x8` 选择现有 kprintf 输出，不设置 HALT 位。
字符写入路径只做内存日志镜像，绝不编码二维码或画屏。每次启动 poll
最多处理一帧，两个通道交替；全局显示节奏约 500ms 一帧。EARLY_BOOT
线程每次睡眠 250ms，实际运行后才扩大当前尾部大小。没有检查点等待。

渲染使用原生内核栈、独立的永久 `ml_io_map` 映射和非阻塞 render guard；
不改 TTBR、TCR、SCTLR，不使用旧 reporter 的共享栈或临时地址空间。
正常输出与图形禁用输出均保留 XNU、ramoops 和 CDC 的内存镜像，
只抑制覆盖诊断画面的 VC 文本。控制台重建后恢复标准条和二维码。
实际映射、线程调度、扫描输出和缓存行为仍须实机验证。

## 来源与验证

官方标准依据 UniXNU `0c1bac3d51a3009dca1708b15a5198f4b43d057a`
的 `scripts/patch-xnu-entry-probe.py` 和调试文档。
二维码编码器原样固定为 Microsoft Mu `b8d46c71610318e36a661819e1e3c0b8bdda413a`，
接收协议固定为 OneSend `39e95ce59df2f2dc38d2556dd4239cec6a0ca35f`。
旧 Mu 的有符号全一掩码使用显式 `-fwrapv` 编译语义，源码字节不改。
所有 UEFI 服务和 QR 全局符号私有前缀隔离，没有调用 UEFI 运行时服务。
XNU 的对象宏 DEBUG 仅在三个 QR 对象的兼容头内解除，再定义 EDK2
调用宏；LiveXnu 和 XNU 本体的调试配置保持原编译语义。

`0013` 添加 ramoops 一致快照，`0014` 单独集成 XNU 启动和显示路径。
真实生产源码、独立捕获缓冲、双通道、早期备份、固定接收器和实际 Mu
分别经过主机检查；实际 macOS arm64e 编译、强钩子、归档、最终代码和
预链接另由 CI 验证。上述结果不等于 CDC 已枚举、实机日志已接收、
根卷已挂载或 macOS userspace 已启动。
