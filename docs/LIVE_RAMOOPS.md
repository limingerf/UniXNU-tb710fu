# TB710FU XNU / ramoops 双实时二维码

当前 ramoops 日志使用内核镜像内 256 KiB 对齐 BSS 缓冲区，仅保证本次
启动期间安全可读。它不再访问未由 XNU 内存分配器排除的固定物理地址，
也不承诺强制重启后保留；Android pstore 跨重启恢复需要另行实现固件和
加载器内存预留。

本组件替换逐检查点两秒回放。两个二维码读取本次启动的实际日志；
屏幕顶部保留固定官方 UniXNU 的绿、蓝、品红三条，每条占
`((rowBytes * height) >> 4) & ~7` 字节。

## 显示与接收

TB710FU 的 3200×2000 帧缓冲并排显示两个实时二维码：

- 左侧 XNU：直接读取独立的 64 KiB XNU 输出环形缓冲。每份文件都带有
  `machine_startup` 前冻结的最多 512 字节早期备份，以及当前最近最多
 3072 字节调试输出。后台线程实际运行前，当前尾部会改用紧凑元数据的
 单帧导出，早期备份保留在内存中并标注为 deferred multi-frame，不会被
 截断后伪装成已导出；线程运行后恢复完整双实时文件。
- 右侧 ramoops：直接读取本次启动内核缓冲区的最近最多 4096 字节；
 后台线程实际运行前使用严格单帧导出（通常最多 512 字节）。它是原始
 日志文本，排除 Linux pstore 头、ECC 和旧启动日志，包含尚未换行的尾部。

ramoops 是当前启动的内核缓冲副本，因此两侧文本可能重叠。它们来自独立缓冲，
不能把两个相似的文件当成两份独立的硬件启动证明。

左侧文件的导出元数据明确区分 early backup 与 current tail 的状态、
真实字节范围和长度；随后依次放置两段原始字节。元数据不是 XNU
控制台输出。早期备份只冻结一次，之后每份左侧文件都重复携带它，
不会随环形缓冲覆盖。冻结时若为空或忙，会明确标注，后续日志不被
冒充成早期备份。左侧在这次冻结完成前显示 pending。

文件名使用 `TB710FU-xnu-live-GENERATION-START-END.log` 与
`TB710FU-ramoops-live-GENERATION-START-END.log`。范围 `[START, END)`
标明各自当前尾部在本次启动成功写入字节流中的位置；左侧的完整文件
还包含元数据和早期备份，因此文件大小可以大于 `END - START`。
两侧均为有界快照，不代表整份启动日志。争用丢弃字符单独计数。

后台线程尚未执行时，单帧接口按实际文件名计算 LMS1/OneSend 容量，超限
尾部只保留最新字节并更新 `[START, END)`，不会静默生成多帧。文件头的
`raw_layout=current_only_single_frame` 和
`earlybackup_export=deferred_multi_frame` 区分这种降级快照；固定 OneSend
接收器可用一张清晰二维码完成 K=1 文件。该模式只解决慢扫码和单次拍照，
不代表后台线程已经调度。

每份文件先固定内容，再轮播数据块；每个通道至少发完 16 轮才更新。
单帧导出（后台线程运行前的降级路径）不同：一个源块拍一张即完整，
因此它只需 2 个完整轮就允许被更新，避免早期停住时右格永远停在启动横幅。
接收使用固定版本 OneSend 原协议。先接收一侧，重置接收器后再接收
另一侧；同一个接收器实例不能混用两个 session。实时文件代次改变时，
该接收器必须 reset 或单独管理新 session，接收端不会把跨 session 的
数据块合并。小屏无法并排时交替显示。

在后台线程尚未运行时，左侧先导出一个单帧文件，优先保留最新 XNU
尾部；早期备份继续留在内存，元数据标为 `deferred_multi_frame`，不会
假装已经放进单帧文件。右侧也使用严格单帧导出。单帧文件可慢速扫码，
线程启动后恢复早期备份加当前尾部的多帧导出。单帧容量不足时只保留
最新尾部并调整真实 `[START, END)` 范围，不把截断内容标成完整日志。
左侧单帧头部约 314 字节，与日志共用同一帧；实测该头部 + 339 字节尾部
正好等于 653 字节单块容量，因此不再压缩头部，避免改动既有解析锚点。

## 停住时的可读性

每一帧都由内核实际执行到 `tb710fu_live_log_poll()` 时推进，因此画面完全
静止就说明没有代码再执行到该函数，而不是渲染故障；一张定格照片能反映的
只是最后一次成功发布的快照。

新停点诊断参数为 `tb710fu-live-checkpoints=1`，必须与 `tb710fu-live-log=1`
同时提供。此模式不启动后台渲染线程，也不让普通 250ms poll 覆盖二维码。
每个显式 startup/kalloc 检查点会先写日志，再同步编码并绘制一个新的 XNU
单帧 OneSend 文件；callback 在调用前和返回后都发布检查点。独立单帧会话
绕过普通快照的 2/16 轮替换门限，因此阶段推进时最后一次成功的 begin QR
会留在 framebuffer 上。若随后内核停住，扫码得到的是停住前的最后成功阶段，
不是停住后的新日志，也不是故障 PC。
每个检查点都是新的 OneSend session；接收器必须先结束或 reset 旧 session，
再接收停住后留在屏幕上的单帧。

同步二维码只带能放进一个 systematic frame 的最新 XNU 尾部和阶段字段；
早期备份仍标记为 deferred，不声称单帧里包含完整控制台历史。capture、编码
或 framebuffer 写入失败时会保留上一帧并计入错误状态。静态主机测试能验证
帧内容与调用边界，不能验证实机面板扫描输出、相机可读性或设备启动结果。
bootstrap 内 `early_random` 的五次调用、kernel list/post tests，以及 thread bind
与 cluster resume 也分别有 begin/done 标记，避免这些相邻子操作仍共用一个边界。

## 保留与覆盖

短日志通常不容易写满 64 KiB 环形缓冲，但密集循环输出仍可能覆盖
最旧的内容。二维码传输期间文件不会被修改，固定的早期备份也不会
被覆盖；这两项保护不能保证保留每个时刻的完整日志。

若 CPU 卡在关闭中断的循环中，实时轮播也会停下。多帧文件只有已经
接收齐才可恢复；仅拍到停止时的一张码不能保证恢复整个文件。此前的
独立固定单帧显示方案已按用户最新选择改为双实时加文件内早期备份。

## 原生边界

检查点诊断的显式参数为 `tb710fu-live-log=1 tb710fu-live-checkpoints=1 debug=0x8 -enable_kprintf_spam startup_debug=1`。
`debug=0x8` 选择现有 kprintf 输出，不设置 HALT 位。
字符写入路径仍只做内存日志镜像，绝不编码二维码或画屏。检查点模式由
startup/kalloc 调用点同步发布 XNU 单帧；不等待线程、轮询节流或 OneSend
多帧收集。未提供 `tb710fu-live-checkpoints=1` 时保留旧双通道 250ms 轮询模式。

渲染使用原生内核栈、内核拥有的当前启动缓冲区和非阻塞 render guard；
不改 TTBR、TCR、SCTLR，不使用旧 reporter 的共享栈或临时地址空间。
正常输出与图形禁用输出均保留 XNU、当前启动 ramoops 和 CDC 的内存镜像，
只抑制覆盖诊断画面的 VC 文本。控制台重建后恢复标准条和二维码。
实际映射、线程调度、扫描输出和缓存行为仍须实机验证。

## 来源与验证

官方标准依据 UniXNU `0c1bac3d51a3009dca1708b15a5198f4b43d057a`
的 `scripts/patch-xnu-entry-probe.py` 和调试文档。
二维码编码器原样固定为 Microsoft Mu `b8d46c71610318e36a661819e1e3c0b8bdda413a`，
接收协议固定为 OneSend `39e95ce59df2f2dc38d2556dd4239cec6a0ca35f`。
旧 Mu 的有符号全一掩码使用显式 `-fwrapv` 编译语义，源码字节不改。
所有 UEFI 服务和 QR 全局符号私有前缀隔离，没有调用 UEFI 运行时服务。
XNU 的对象宏 DEBUG 仅在三个 QR 对象的兼容头内解除，再定义 EDK2
调用宏；LiveXnu 和 XNU 本体的调试配置保持原编译语义。

`0013` 添加 ramoops 一致快照，`0014` 单独集成 XNU 启动和显示路径，
`0015` 将 ramoops 改为内核拥有的本次启动 BSS 缓冲区并移除物理映射。
状态行还显示每路二维码编码成功数和 framebuffer 写入成功数。`ready` 只表示
源快照与传输帧可用，并不证明编码或显示写入成功，也不证明面板扫描输出或
相机解码正常。补丁 `0016` 曾只记录 KMEM rank-0 返回；新版 `0017` 在 live-log 启用时为每个 startup callback 记录 subsystem、rank、arg 的返回 marker，并调用受 250ms 全局节流限制的轮询。这样一次构建即可覆盖任意启动阶段，不再逐阶段增加 marker；不修改 callback、顺序或 compressor 容量策略。
新补丁 `0022` 将 startup callback 与 kalloc 检查点改为同步单帧发布；检查点
模式不启动竞争 renderer worker，并保留 callback begin/return 两侧边界。
打包门禁要求新 boot argument 与 live-log 同时出现，native integration 检查
startup.o 与 kalloc.o 对强 provider 的实际分支。此设置把停点前最近阶段留在
屏幕上，但仍不提供内核停住后的后台刷新。

真实生产源码、独立捕获缓冲、双通道、早期备份、固定接收器和实际 Mu
分别经过主机检查；实际 macOS arm64e 编译、强钩子、归档、最终代码和
预链接另由 CI 验证。上述结果不等于 CDC 已枚举、实机日志已接收、
根卷已挂载或 macOS userspace 已启动。
