# TTBR1 Snapshot and Low-Address Guard

The QR8 report ends at stage 47, immediately before the marked TTBR1 helper call. Its `ARG0` is the candidate root, but it contains no descriptors. The post-link candidate recorded in [kernel-ttbr1-snapshot-build.json](evidence/kernel-ttbr1-snapshot-build.json) adds a read-only walk of that root at the same checkpoint and a separate low-address exception path for the switch window.

The captured TCR `0x00080022a51a251a` has `T1SZ=26` and `TG1=2`: a 38-bit TTBR1 address space with 4 KiB pages, starting at L1. The walker handles L1 1 GiB blocks, L2 2 MiB blocks and L3 pages, including effective `PXNTable` and `APTable` restrictions. It only supports this observed geometry. Before reading a descriptor, `AT S1E1R` verifies that the old TTBR1 linear alias translates back to the requested physical page. An inaccessible alias or unsupported geometry is reported without dereferencing the page.

The report explicitly identifies `STAGE=47` and uses compact low-48-bit virtual addresses; their canonical upper bits are `ffff`. Each target row contains its role, VA, raw L1/L2/L3 descriptors and a status. `H` is the switch helper, `R` the kernel return PC, `S` the stack, `V` the original exception vectors, `C` the reporter continuation and `N` the first post-switch `_set_mmu_ttb` call. `X` and `D` count reporter RX and RW-NX pages that match the expected physical mapping and permissions. If a range has a failure, the report includes the first failing page and its descriptor chain.

The guard builds a separate low-address TTBR0 identity map from the currently active old TTBR1 mapping, so its exception path does not depend on the candidate root being tested. It requires the observed TTBR0 4 KiB geometry and one L1/L2 region for the reporter image. It converts the old root's checked leaf or block attributes to 4 KiB identity pages, verifies low-address read/write translations and effective execute permissions, installs a low VBAR and returns from a deliberate `BRK #0xb712` self-test before entering the TTBR1 helper. The test restores `TPIDR_EL1` and `TPIDRRO_EL0`; the fault handler records the exception through the physical alias and switches to its emergency stack only after saving the fault state.

The GOP renderer temporarily replaces TTBR0 while drawing. Its temporary table now carries the guard's vector, state and stack mappings too. If guard preparation or translation checks fail, the code restores the old TTBR0 and VBAR and continues with the original vector path. If the helper returns, the code restores the high XNU VBAR first, then restores the original TTBR0 and TCR before continuing.

The guard status is `0` before preparation, `1` after the identity tables are prepared, `2` after the low-address BRK self-test returns, and `3` when setup fails and the original mapping is retained. The stage-47 report records this status.

The latest user-supplied stage-47 report showed candidate root `0x8c8905000`. Its `_set_mmu_ttb_alternate_probed` helper, kernel return PC, stack, original vectors and first post-switch `_set_mmu_ttb` target were mapped. The diagnostic continuation was not: `C` had an invalid L3 descriptor, `X=0/12` for `__KDIAG`, and `D=0/200` for `__KDATRW`. This snapshot is before the helper call, so it does not prove a TTBR1 switch fault. The reported `G=3` came from the then-tested guard implementation mistakenly sourcing its identity table from the candidate root under test.

guard9 changes the guard source to the active old TTBR1 root from `O1`. It accepts a broader old mapping only when the physical address and required access (execute for code, write for state) are valid, then creates stricter RX and RW-NX identity PTEs. The rebuilt and signed pair is in `out/kernel-ttbr1-guard9/`; it has not been booted, so its hardware guard status remains unknown.

The candidate keeps the QR8 checkpoints 47/48, 49/50, 51/52, 54 and 55/56. Local AArch64 instruction models, exception capture tests, the synthetic TTBR0/GOP table merge test and the pinned OneSend receiver passed. The paired `vendor_boot.img` and `vbmeta.img` in `out/kernel-ttbr1-guard9/` are signed with the existing test key and independently verified. These tests do not verify the device's caches or prove a hardware exception reaches the guard. The signed pair has not been booted.

## Guard10: Marker Fault Diagnosis

The later `XNU EARLY EXCEPTION` report is a write translation fault on the diagnostic marker, not a captured TTBR1 table fault. `ESR=0x96000045` has `WnR=1` and `DFSC=0x05` (level-1 translation fault); `FAR=0x93ffff000`. The helper starts at `0xfffffff00bb8b360`, making `ELR=0xfffffff00bb8b374` its first `STRB`. `SWITCH_GUARD=2` says the low reporter/vector BRK test returned; it did not test the marker page. The report is consistent with guard9 exposing a hole in its own TTBR0 map before the XNU TTBR1 write. The device partition hash was not read back, so the exact flashed package is not confirmed.

Guard10 maps `0x93ffff000` identity RW-NX through L1/L2/L3 (`0x24`, `0x1ff`, `0x1ff` for the observed geometry), checks it with `AT S1E1W`, and clones it into the GOP temporary root. Its test executes both literal marker stores under the guard root, the T0SZ=25 GOP root, and the restored guard root. The page-walk permission test also corrects APTable handling: bit 61 blocks EL1 writes; bit 62 restricts EL0.

The candidate reuses the exact verified prelink from run 43844823907 and does not rebuild XNU. A later user screenshot labeled guard10 shows stage 48, followed by the reporter fault described below; the device partition hash was not read back, so exact image attribution remains unverified. The signed images and original build checks are recorded in [kernel-ttbr1-guard10-build.json](evidence/kernel-ttbr1-guard10-build.json). The package is diagnostic and does not claim a functional XNU fix.

## Guard10 Follow-up: Fileset Header Lookup

The later `src-045bfc7c-guard10` screen reached `XNU returned: vm/set_mmu_ttb_alternate_probed#1`. Its `ESR=0x86000007` is a current-EL instruction abort with an L3 translation fault. `FAR=ELR=0xfffffff00f82ba10` is `diag_live_text+0x284`, in the fourth 4 KiB page of `__KDIAG`; the expected instruction is `CMP X22, X27`. The helper returned, then the reporter fetched code absent from the active TTBR1 map. This does not identify a failure in the TTBR1 switch helper.

The cause is the Mach-O header used by patch 0006. Post-linking adds `__KDIAG` and `__KDATRW` commands to the outer `MH_FILESET` header, while `_mh_execute_header` points to the embedded `com.apple.kernel` `MH_EXECUTE`, which has neither segment. The lookups therefore returned null and skipped both mappings. Patch 0006 now selects `PE_get_kc_header(KCKindPrimary)` for filesets, keeps `_mh_execute_header` for standalone kernels, and skips safely if the selected header is unavailable. Guard11 has passed the supported macOS native/prelink build and is signed; its fileset-page mappings still need a device report to verify. See [guard11 evidence](evidence/kernel-ttbr1-guard11-build.json).

The project has no proven generic CDP/XNU USB logging path. EUD appears in the live device tree and firmware strings, but host enumeration and a matching XNU driver are not established. The official USB debug terminal uses a giulia-specific protocol. No device-side test was performed for this update.
